### 正文（中文，可直接复制）

```text
项目地址在文末。先说为什么做，以及几个实现上的取舍。

【问题】
我有一份西语词汇数据，最早是“单词 + 释义 + 例句”的表。后来发现两个问题：
1. 释义和例句基本来自词典，属于受版权保护的汇编，不适合直接开源分发；
2. 数据一旦静态化就开始过期，改一个词要同时维护单词表、级别表、例句表。

于是我把内容层整个删掉，只保留结构层。

【数据模型】
三个 YAML：

data/raices.yaml
- id: pac
  root_name: pac
  latin_origin: "pax, pacis (peace)"
  batch: b9

data/relations.yaml
- source: pac
  target: paz
  rel_type: derivar
  cefr_level: A2
  prompt_template: null

data/afijos.yaml：词缀 id / affix / meaning / type，目前参与校验和统计，暂不渲染为图节点。

关系类型只有三种：derivar（派生）、asociar（语义联想）、confundir（易混）。
没有独立的单词表：一个词之所以存在，是因为某条边指向它；CEFR 级别挂在派生边上。
这样做的好处是不会出现“单词表加了词、关系表忘了加边”的漂移。

【生成管线】
1. scripts/generate_mermaid.py
   先校验：字段白名单、关系完整性、CEFR 枚举、重复边、自环、以及“是否混入释义/中文解释”的泄漏检查。
   校验通过后，为每个词根生成一页 Markdown（含一个 Mermaid graph），再生成 A1–C2 六个分级清单。
2. scripts/build_no_raiz.py
   生成无法用拉丁词根拆解的高频词清单（原生词、阿拉伯/日耳曼借词、功能词、不规则动词），目前 364 条。
3. scripts/build_site.py
   读取上面生成的 Markdown，从每个词族页里抽出 fenced Mermaid block，连同索引表一起内联成一个 index.html。
   没有前端框架、没有 bundler；Mermaid 固定版本，从 CDN 加载。
4. .github/workflows/pages.yml
   push 到 main 后：重新生成 mindmaps/levels/no-raiz → 构建 site → 上传 Pages artifact → 部署。
   site/ 是构建产物，已 gitignore；仓库里只提交数据和脚本。

【为什么把生成物也提交进仓库】
- GitHub 能直接渲染 Mermaid，clone 下来就能看；
- 生成物可作为“数据是否同步”的证据：CI 里重新生成后如果出现 diff，说明有人手改了生成物或忘了提交数据；
- 纯文本可 diff、可 review，PR 里能直接看到图的变化。

【AI 的边界】
每条词形都带一个 URL-encoded 的预置 prompt。默认跳豆包，只是因为模板是中文；仓库本身不调用任何模型，不存 API key，也不存回答。
用户可以把同一条 prompt 粘贴到任意 LLM。仓库负责“地图”，模型负责“内容”。

【已知问题】
- 网页版首次加载依赖 Mermaid CDN，不是完全离线；仓库视图才是离线可用的。
- 图是一族一页，不做一张全量大图，Mermaid 在节点数上去之后布局会明显变差。
- CEFR 是教学参考，不是官方 DELE 词表。
- 232 个词根 / 1,423 个词只是当前规模，不是全量。

【想听的意见】
- “级别挂在边上”这个建模是否合理？还是应该单独建 word 表？
- 三种关系类型够不够？有没有更细的语义关系值得拆？
- 生成物入库 + CI diff 检查，在更大的数据集上会不会变成负担？

项目地址：https://github.com/auding1900/es-raiz-vocab
在线站点：https://auding1900.github.io/es-raiz-vocab/
```

## 渠道 B：掘金 / 知乎技术短文

### 标题备选（3）

1. `如何用 YAML + Mermaid + Python 构建一个“不存储内容”的知识仓库`
2. `从 232 个词根到静态站点：一个纯文本知识库的构建管线`
3. `为什么我把释义从仓库里删掉了：结构、生成物与 AI 的边界`

### 短文结构（约 1,500–2,000 字）

**开头（150 字）**

> 这是一个西语词根项目，但本文主要讲工程实现：怎么用三个 YAML、两个 Python 脚本和一个 GitHub Actions workflow，把一个“只有结构、没有内容”的仓库变成可浏览的静态站点。项目不是 DELE 词表，也不提供词典释义。

**1. 问题：内容层让仓库不可维护（250 字）**

- 释义/例句来自词典汇编，版权与分发风险；
- 静态内容会过期；
- 单词表、级别表、关系表三处漂移。

**2. 数据建模：把级别挂在边上（400 字）**

- `raices.yaml` / `relations.yaml` / `afijos.yaml` 的字段；
- 为什么没有 word 表；
- `derivar` / `asociar` / `confundir` 三种边；
- 重复边、自环、CEFR 枚举的校验；
- 字段白名单与“释义泄漏”检查。

**3. 生成：Markdown 是中间产物（400 字）**

- 一页一根，一个 fenced Mermaid block；
- 分级清单从同一份 relations 生成；
- 生成物提交进仓库的理由；
- CI 重新生成 + diff 检查。

**4. 站点：不引入前端框架（350 字）**

- `build_site.py` 读取索引表；
- 从每个词族页抽取 Mermaid block；
- 内联 JSON + 单页 HTML；
- Mermaid 固定版本；
- hash 路由、去重音搜索、复制 prompt；
- `site/` gitignore，由 CI 构建。

**5. AI 边界（250 字）**

- prompt 模板 URL 编码；
- 仓库不调用模型、不存 key、不存回答；
- 默认豆包只是链接目标，prompt 与 provider 无关；
- 为什么不把 AI 生成内容写回仓库。

**6. 取舍与遗留问题（250 字）**

- CDN 依赖与“离线可用”的边界；
- 一族一页 vs 全量图；
- 232 个词根的规模上限；
- 想听的意见：边上分级是否合理、关系类型是否够用、生成物入库的长期成本。

**文末**

> 项目地址：https://github.com/auding1900/es-raiz-vocab

## 预期质疑与回应思路

| 质疑 | 回应思路 |
| --- | --- |
| “为什么不用数据库？” | 目标是 diff-friendly、PR-friendly、可离线阅读；数据量在千级，YAML + git 足够。真要上量再换 SQLite/Postgres 也不难。 |
| “生成物为什么入库？” | 让 GitHub 直接渲染、让 clone 即可读，同时用 CI diff 检查数据与产物是否同步。 |
| “Mermaid 性能怎么样？” | 一族一页，单页节点数有限；不做全量图。节点再多会考虑预渲染 SVG。 |
| “没有释义的词汇库有什么用？” | 定位是索引/导航层，不是词典；释义由用户在查询时用自己的模型生成。 |
| “AI 生成内容不可靠。” | 仓库不存 AI 回答；prompt 要求引用公版文本并标注古体；用户仍需自行核对。 |
| “为什么只有 232 个词根？” | 当前是种子集，不是全量；数据可扩展，欢迎 PR。 |
| “为什么 Python 3.9 / 不用 TypeScript？” | 脚本只做文本生成，Python 标准库 + PyYAML 够用；少一层构建链。 |
| “为什么默认豆包？” | 预置 prompt 是中文；换成任意模型都可以，链接只是默认入口。 |
